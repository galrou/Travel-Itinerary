# Feedback interpretation is a separate Protocol from RequirementsExtractor

Ticket 08 needs to turn a traveler's free-text follow-up (e.g. "swap lunch for a cafe") into a targeted Slot edit against an already-built Itinerary. We considered extending the existing `RequirementsExtractor` Protocol — one LLM-facing extraction interface for all free-text-to-structured-data work in the graph — rather than adding a second one. We decided against it: `RequirementsExtractor`'s contract is "free text → Requirements fields, missing-value-safe," with no awareness of an existing Itinerary. Feedback interpretation needs the current Itinerary/Day as input (to know what "lunch" currently is) and produces a different output shape (a targeted Slot plus replacement criteria, not a `Requirements` object). Overloading `RequirementsExtractor` with an optional second responsibility would make its interface lie about what it does. We introduced a new `FeedbackInterpreter` Protocol instead, mirroring `RequirementsExtractor`'s shape (a Protocol with no real implementation yet, mocked in tests) but scoped to its own input/output contract. If a future need arises to merge these into one general "LLM extraction" concept, that will require redesigning both interfaces together — it is not a change that falls out for free.
